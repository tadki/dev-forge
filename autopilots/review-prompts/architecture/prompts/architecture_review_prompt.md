> 版本：v2.3（2026-08-28，Owner 指令 SEE-1191 第八轮：补 refactor 覆盖缺口；v2.1 结构重组——拼装产物连续编号为 §1 评审任务（当期主题与对标参考注入 §1.1）/ §2 指引和规则（要做的事 + 禁止做的事）/ §3 产出；禁止行为全篇归一；删除防疲劳独立节与解释性缀语；与 toolchain v2.1 同步）
> 调度方：Multica autopilot `a08b4ae1-737f-4c63-bc6f-fa0943b965f1`（每周二 / 周五 03:00 Asia/Hong_Kong）
> 执行方：具备仓库只读访问权限的评审 agent（默认 Refacty；可按主题轮换或固定）
> 性质：模板（prompt 文本），非可执行脚本。**拼装已脚本化**：执行 agent 每期运行 `dev-forge/review-prompts/architecture/build_review_prompt.py`，脚本输出即当期完整评审 prompt（期次自增、四主题轮换、当期对标参考随主题注入、占位符替换、Kill Switch 检查均已内置）。本文件是脚本的拼装素材与设计规格。
> **章节归属约定**：「§N」指拼装产物中的第 N 节（§1 评审任务 / §2 指引和规则 / §3 产出）；本文件第 4-7 节为主题素材，仅供脚本按期取材注入 §1.1，不独立出现在拼装产物中。
> **指引粒度约定（Owner 指令）**：本模板只给框架与方向——评什么主题、什么算好、怎么汇报、什么不能做。**不规定怎么查、查哪些文件、跑哪些命令**；具体执行方法由评审 agent 自主决定，允许发挥。

## 2. 指引和规则

### 2.1 要做的事

- 评审前先了解以下背景，不要凭空假设：
  - 仓库 master 分支（只读）。游戏代码域：`autoload/`、`systems/`、`scenes/`、`resources/`、`tests/` 等，按主题自行决定探索范围；
  - 最近 7 天架构日检产物：`{{daily_report_dir}}`；
  - 上一期半周检台账：`{{ledger_path}}`（用于趋势线比对与条目去重）；
  - 按主题用 hindsight recall 检索过往架构决策与教训。
- 评审完成后把本期条目追加到台账 `{{ledger_path}}`，供下期去重与趋势比对。
- 评审过程中遇到结构看不懂、上下文不足以支撑判断的情况时，先用 `/recall` 召回相关记忆（历史决策、既有教训）再下结论，不要靠猜。
- 遇到已拍板裁决的违反项直接提报，不需重新论证：消耗类数值必须 effect 化（OQ-1）；派生值永不入 save（OQ-3）；类型分发走 Registry 而非核心 switch（SEE-1148）。
- 遇到 CRITICAL 级问题按红线升级通道处理（见 §3.4）。
- 评审自身运行失败时：只在台账 `errors:` 字段记一行，不发汇报评论、不重试（连续 2 次失败由日检阈值捕获）。

### 2.2 禁止做的事

- 不修复、不重构、不写代码（只评审）；
- 不新开任何 issue / discussion——检查汇报只发一条评论到本次执行 issue（见 §3）；
- 不自动 @ 任何人、不设 assignee、不催办；
- 不重复提报台账中已存在且状态未变化的条目（去重规则见 §3.3）；
- 不评审工具链（dev-forge 仓库 hooks / autopilots / toolchain 等，属工具链半周检范围）；
- 不评审 skills / Multica 平台配置；
- 不触碰 `addons/godot_mcp/`（vendored 只读红线）。

## 3. 产出

评审完成后做三件事：① 把 §3.1 骨架改写/填空（删占位行）写入 `./architecture_review_report.md`；② 以该文件为正文发评论到本执行 issue；③ 把本期条目追加到台账。

```bash
multica issue comment add <本执行IssueID> \
  --content-file ./architecture_review_report.md
```

无新发现仍发（正文写「本期无新发现」+ 趋势线）。

### 3.1 报告骨架（评论正文与台账条目共用）

每条建议须具备六个字段，缺一不可：维度 / 位置 / 问题模式 / 对标最佳实践 / 优化方向 / 预估收益。数量不设上限，按预估收益排序；低收益且暂无演进动力的条目放"暂缓"区。

```markdown
## 本期元信息

- 期数：第 {{nth}} 期
- 日期：{{date}}
- 主题：{{theme_zh}}
- 执行 agent：{{executor_agent}}

## 新增建议（无则写「本期无新发现」）

| # | 维度 | 位置 file:line | 问题模式 | 对标最佳实践 | 优化方向 | 预估收益 | fingerprint |
|---|------|----------------|----------|--------------|----------|----------|-------------|
| 1 | | | | | | | |

## 上一期条目状态更新（无则写「无」）

- fingerprint `...`：仍存在 / 已修复 / 部分修复（一句话证据）

## 趋势线（首期写「首期，无上期」）

| 指标 | 上期 | 本期 | 方向 |
|------|------|------|------|
| | | | |

（按当次主题自选 3-5 个关键指标）

## 暂缓区（无则写「无」）

## CRITICAL 提案区（无则写「本期无」）

- （如有：标题 + 问题描述 + 建议负责人；台账同步打 `severity: CRITICAL`，由日检转草稿走 Owner 审批）
```

### 3.2 台账

追加本期条目到 `{{ledger_path}}`（`review-prompts/architecture/ledger/YYYY-MM.md`，每个主题一节，含 fingerprint 全量明细），供下期去重与趋势比对。

### 3.3 条目去重

`fingerprint = sha1(规范化(file) + line + 模式关键词)`。下期评审时：fingerprint 已存在且状态未变化 → 不重复提报，只在「上一期条目状态更新」写一行；严重度上升 → 重报并注明升级；已修复 → 标注「已修复 + 证据」。同一 fingerprint 72h 内不重复提报。

### 3.4 红线升级通道

如评审中遇到 **CRITICAL**（架构层面存在严重缺陷、可能导致系统不稳定或数据丢失），不自行开整改 issue、不自动 @ 任何人。改为：

1. 在台账该条目上打 `severity: CRITICAL` 标签；
2. 在条目末尾添加 `proposal:` 字段，写一份**草稿 issue 提案**（标题 + 一段问题描述 + 建议负责人）；
3. 在当期汇报评论的「CRITICAL 提案区」同步列出该提案；
4. 由日检在每日扫描时把台账中新增的 `severity: CRITICAL` 条目转成正式草稿 issue，走 Owner / Atlas 审批通道。

## 4. 主题素材 A · 数据流与耦合（第 1 / 5 / 9 ... 期注入）

关注"数据怎么流动"：数据所有权决定谁写、耦合模式决定谁读、二者共同决定系统的可演化性。核心方向——每份核心状态是否有单一写权威；数据下行 / 事件上行的方向是否清晰；effect 通道之外是否出现旁路直写；EventBus 与 autoload 自身 signal 是否双轨漂移；派生值是否入档。

本期对标参考（按需引用，不要硬套）：Flux/Redux 单向数据流；ECS 的 System 独占写；事件溯源 / CQRS；Godot 官方 signal-up / call-down；《DOOM》Command Buffer。

---

## 5. 主题素材 B · 状态机与生命周期（第 2 / 6 / 10 ... 期注入）

关注"时间与顺序"：状态机管理"什么时刻可以做什么事"，资源生命周期管理"什么时刻加载/释放什么资源"。核心方向——复杂流程是否用显式状态机建模而非布尔字段组合；autoload 初始化顺序的依赖契约是否显式；scene 树与 Resource 的职责与生命周期划分；资源加载策略（preload vs lazy）；异步流程（加载、接管、重生等）是否显式建模、死守卫与反射调用的死代码。

本期对标参考（按需引用，不要硬套）：HFSM（层级状态机）；Unreal GAS；《Celeste》Scene 即组件 + Autoload 极少；《Hades》Resource 数据驱动；Unity Addressables（懒加载 + 句柄化）。

---

## 6. 主题素材 C · 模块边界与扩展点（第 3 / 7 / 11 ... 期注入）

关注"代码怎么组织"：模块边界决定"职责怎么切"，扩展点决定"新增能力怎么接入"。核心方向——autoload 的职责单一性与数量膨胀；模块对外接口面是否失控；跨模块调用是否经 effect / event 而非直改内部状态；新增类型是否经注册机制接入（OCP）而非修改核心代码；注册是否幂等、可注销；是否存在两处以上重复实现、该提取共用模块的代码。

本期对标参考（按需引用，不要硬套）：微内核 + 插件式 gameplay system；《Overwatch》ECS System 单一职责；Godot 官方 autoload 指南；Registry/Composite 模式。

---

## 7. 主题素材 D · 可测性与反模式（第 4 / 8 / 12 ... 期注入）

关注"架构能否被验证"。核心方向——测试的存在性 / 有效性（真实断言还是空跑恒真）/ 可信度（是否真在跑、失败是否被吞）；effect 应用可追踪、事件可重放；已知反模式的增量扫描（God Object、隐式布尔状态机、双轨通信、死守卫、旁路直写、派生值入档、跨层直连、注册缺失的 switch、autoload 膨胀、时序耦合、无人调用的函数/过期实现——清单为已知枚举而非全集，清单外发现同样欢迎提报）。

本期对标参考（按需引用，不要硬套）：《Forza》回放系统；id Software deterministic lockstep；Godot GUT + headless CI；Google Testing Blog "Just Say No to More End-to-End Tests"；ThoughtWorks 测试金字塔。
